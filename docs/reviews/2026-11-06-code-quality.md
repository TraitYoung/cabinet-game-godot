### Q01 · P1 · Docker 数据库路径未持久化

- 状态：已修复（2026-11-08）。固定容器数据库路径，挂载独立 `api-data` 卷；本机路径不受覆盖。
- 位置：`scripts/setup_linux_env.sh:63`、`docker-compose.yml:37`、`infrastructure/container.py:53`。
- 触发条件：初始化脚本将 `AX_DB_PATH` 写为宿主机 `$HOME/.axiodrasil/axiodrasil_core.db`，随后使用 Compose 启动 API。
- 问题：Compose 将 `.env` 中的路径传入容器，但只把仓库挂载到 `/app`，没有挂载对应的数据库目录。数据库落在容器文件系统中，重建容器可能丢失原始聊天记录和情绪状态。Hindsight 的独立命名卷不受此问题影响。
- 修复建议：为容器指定固定数据库路径，并为该目录配置持久化挂载；区分宿主机与容器的路径配置。
- 验收：使用临时测试数据写入聊天与情绪状态，重建 API 容器后仍能读取；同时验证本机启动路径保持可用。

### Q04 · P2 · 取消或超时后，后台回合仍可能提交

- 状态：已修复（2026-11-08）。持久化请求 ID 与提交状态，事务决定取消边界；断线和前端停止/超时按服务端状态处理。
- 位置：`main.py:88`、`main.py:359`、`frontend/src/modules/solo-chat/SoloChatView.tsx` 的停止与超时处理。
- 问题：浏览器中止请求不会停止已经运行的工作线程。线程仍可能完成模型调用，并通过 `after_turn` 写入聊天和长期记忆；前端却提示“已停止这一轮”。用户立即重试时还可能产生重复或并发回合。
- 复现：用事件阻塞回合生成，取消等待它的 HTTP 协程，再释放工作线程；观察到 `after_turn` 仍被执行。实验使用模拟服务，没有调用外部模型或写入真实记忆。
- 修复建议：定义取消与提交的边界，在可取消阶段向服务层传递取消状态；引入请求 ID 和幂等提交。已提交时应向用户准确反映状态。
- 验收：分别覆盖生成中取消、提交期间断线、客户端超时与重试；验证是否落库符合约定，同一请求不会重复提交。

### Q05 · P2 · 同一会话的并发请求破坏对话顺序

- 状态：已修复（2026-11-08）。统一回合入口使用跨进程会话锁；冲突返回 409，锁覆盖上下文读取至提交结束。
- 位置：`modules/chat_api/service.py:65`、`main.py:88`。
- 问题：读取历史、生成回复和保存回合之间缺少会话级并发控制。多个标签页或取消后重发可能让后一条消息基于过期历史生成，并按完成顺序写入。
- 复现：两个请求使用同一会话，在生成阶段通过屏障同步；两者都读到空历史。控制第二条先完成后，保存顺序为“第二条、第一条”。实验使用临时 SQLite 和模拟模型、记忆服务。
- 修复建议：在统一回合入口对同一会话进行串行处理或明确拒绝并发；保护范围应包含读取上下文到提交完成的全过程，并与 Q04 的幂等机制协调。
- 验收：同一会话的后续回合能看到前一回合提交结果，顺序稳定；不同会话仍可并行处理。

### Q06 · P2 · 上传中的附件串入另一会话

- 状态：已修复（2026-11-08）。上传绑定 AbortController 与会话生命周期，忽略迟到结果和错误，统一释放预览 URL。
- 位置：`frontend/src/modules/solo-chat/SoloChatView.tsx:399`，尤其是等待上传后调用 `setAttachments` 的逻辑。
- 问题：上传处理未绑定会话生命周期。切换会话会清空已有附件，但旧上传返回后仍会加入当前附件列表。
- 复现：在会话 A 上传文本附件，阻塞模拟附件接口；切换到 B，再释放上传结果。附件出现在 B，发送 B 的消息时，请求正文包含 A 的附件内容。
- 修复建议：切换会话时取消上传并忽略迟到结果，或将附件状态按会话独立保存；错误状态也需要核对原会话。
- 验收：覆盖上传期间切换、新建、结束会话以及组件卸载；旧附件和错误不会进入新会话，预览资源得到释放。

### Q07 · P2 · 后台心跳覆盖用户交互时间

- 状态：已修复（2026-11-08）。新增并迁移 `last_interaction_at`，后台心跳只更新漂移时间；用户交互原子领取提示。
- 位置：`state/mood_engine.py:182`、`state/mood_engine.py:223`、`agents/proactive.py:218`。
- 问题：`compute_interaction_hook` 使用 `last_tick_at` 判断久别和每日首次交互，而空闲心跳也更新同一字段。状态漂移时间被误当作用户最后交互时间。
- 复现：设置上次交互为三小时前，本可得到“两小时”欢迎提示；先执行一次空闲心跳，再计算提示，结果变为空字符串。
- 修复建议：分别持久化最后用户交互时间与状态漂移时间，空闲心跳仅更新后者；兼容已有状态记录。
- 验收：连续后台心跳后仍能正确识别两小时未交互、跨日首次交互，并避免重复触发。

### Q08 · P2 · 情绪状态并发更新丢失

- 状态：已修复（2026-11-08）。状态修改在 `BEGIN IMMEDIATE` 事务内完成，并以实例锁保护嵌套操作和提示状态。
- 位置：`state/mood_engine.py:295`、`state/mood_engine.py:314`，以及其他分离的读取、修改和保存操作。
- 问题：状态读取与保存使用独立数据库连接，整个修改过程没有事务或互斥保护。聊天线程和主动消息线程修改同一身份时，后保存者可能覆盖另一项更新。
- 复现：通过屏障让两个线程读取相同初始状态，各增加 `valence=0.2`；最终值为 `0.2`，而非 `0.4`。
- 修复建议：保证状态读取、计算和写入的原子性；保护范围覆盖漂移、增量和连接重置，避免只修复单一调用点。
- 验收：并发增量不丢失，重置与漂移结果符合约定，数值继续满足边界限制。

- 验收：长用户文本、长回复、附件及多轮历史下，近期双方消息仍有合理保留，整体预算受控。
