# 可维护性检查 · 2026-11-08

本轮基于当前工作区检查维护成本、模块边界与扩展风险。覆盖 HTTP 与异步回合、主动消息、SQLite、前端状态、配置、启动器和测试组织。前一轮 Q01–Q09 的行为修复仍保留，本记录最初提出 M01–M10 待优化项，现已完成整改。以下保留检查时的问题现场，当前解决结果与验证证据见[解决汇报](2026-11-08-maintainability-resolution.md)。

## 结论与顺序

先处理会改变运行行为的边界不一致，再拆分职责和补齐质量门禁。文件长度只作为定位线索，不是独立的缺陷依据。

## M01 · 启动器跨平台行为分叉

- 位置：[Windows 端口清理](../../launcher/stack.py#L281)、[停止流程](../../launcher/stack.py#L433)、[Linux 归属验证](../../scripts/stack_process.py#L12)。
- 现状：Linux 已使用进程组和随机标识验证归属；Windows 启动器仍对记录 PID 直接 `taskkill /F /T`，按 3000/8000 端口查占用者并终止，还会在 WSL 执行全局 `pkill -f 'next dev|next-server'`。
- 影响：同一项“停止本项目”的修复需要维护两套实现，旧入口仍可能终止其他项目。前轮 Q03 的 Linux 回归不能证明 Windows 入口也符合相同规则。
- 验证：仅模拟 `_port_owner_pids` 和 `subprocess.run`，给出未经归属验证的假 PID 后，确认会生成 `taskkill` 命令；未运行实际终止命令。
- 建议：先约定跨平台统一的进程记录与归属策略，再由平台适配负责识别和终止；不要让 Windows 入口按端口或通用名称兜底杀进程。无需为了共享策略重写整个 GUI。
- 验收：两个入口都覆盖旧 PID、PID 复用、外部端口、同名其他项目及子进程残留；真实 Windows 行为需在对应环境验收。

## M02 · 主动消息在回合服务之外保存

- 位置：[主动消息写入](../../agents/proactive.py#L231)、[注入的保存回调](../../main.py#L63)、[用户回合互斥与提交](../../modules/chat_api/service.py#L107)。
- 现状：用户回合经过会话锁、请求状态和 Hindsight 提交；主动消息通过回调直接 `append_turn`，不走会话锁、请求 ID 或长期记忆路径。该差异没有在统一的消息提交接口中表达。
- 影响：用户生成期间，主动消息仍能插入该会话历史；后续改动若假设所有写入都受会话锁保护，会得到错误结论。主动消息是否进入长期记忆、怎样避免将系统标记当作用户事实，也缺少明确的服务契约。
- 验证：在临时数据库持有同一会话锁时调用当前保存回调，原始聊天仍成功新增一条记录。未调用真实模型。
- 建议：提供明确的主动消息提交入口，共享必要的会话互斥和存储边界，同时保留消息来源；单独定义主动消息的长期记忆语义，不直接伪装成用户回合。
- 验收：用户回合与主动消息同时触发时顺序明确、不会读写穿插；写入失败不发成功通知；不同来源的记忆规则有独立测试。

## M03 · 两套取消协调器与同步数据库操作

- 位置：[HTTP 等待逻辑](../../main.py#L107)、[适配器异步入口](../../modules/chat_api/service.py#L150)、[SQLite 超时与连接](../../storage/turn_requests.py#L23)。
- 现状：`_await_turn` 与 `aexecute` 各自创建任务、处理完成回调和取消。两条异步路径都在 `finally` 同步调用 `cancel`；后者可能创建连接并等待 SQLite 写锁，连接超时为 10 秒。
- 影响：改一处取消边界需同步另一处；数据库忙时，原本用于保持响应的异步层反而阻塞事件循环。历史/导出接口中也有在 `async def` 内直接执行同步数据库或文件操作的情况，应按同一原则核对。
- 验证：临时数据库写锁保持约 350 毫秒时触发取消，独立心跳协程最大间隔约 432 毫秒，确认同步等待阻塞了事件循环。该数值是一次实验结果，不是性能基准。
- 建议：保留一个可测试的回合异步协调入口，HTTP 只提供断线信号与响应适配；同步存储操作放到工作线程或同步路由中。继续保留“生成可取消、提交继续”的事务边界。
- 验收：JSON、SSE 和适配器共用取消语义；SQLite 被占用时其他请求与计时器仍能运行；覆盖取消时数据库异常，不覆盖原始异常。

## M04 · 数据契约和迁移边界不明确

- 位置：[请求表与状态](../../storage/turn_requests.py#L12)、[按列序插入](../../storage/turn_requests.py#L66)、[直接写聊天表](../../storage/turn_requests.py#L87)、[生成结果序列化](../../modules/chat_api/service.py#L130)。
- 现状：请求记录返回无明确类型的字典，状态在 Python 与 TypeScript 中以字符串分散使用；`TurnResult.__dict__` 直接成为持久化格式。`TurnRequests` 还知道 `ChatHistory` 的 SQL 列结构，依赖调用者提前初始化聊天表。数据库初始化分别散落在三个存储模块，没有显式迁移版本。
- 影响：改字段、状态或结果类时，难以判断旧数据库和已保存结果能否继续读取；单纯给请求表加列也可能破坏现有插入。
- 验证：临时请求表增加一个可空列后，`begin` 的按列序插入报“7 columns but 6 values”；这是演进脆弱性实验，不是当前未迁移表上的运行错误。
- 建议：SQL 显式列名；为状态、记录与持久化结果定义小而明确的类型及版本；在存储层表达“保存聊天和提交状态”的原子操作；为已存在数据库提供可重复执行的迁移入口。无需引入大型 ORM。
- 验收：老表、额外可空列、旧结果版本和新状态均有兼容测试；事务回滚不产生半条回合；业务服务不依赖表初始化顺序。

## M05 · 前端主组件的状态职责过于集中

- 位置：[SoloChatView](../../frontend/src/modules/solo-chat/SoloChatView.tsx#L80)，尤其是附件处理和发送/恢复逻辑。
- 现状：组件约 804 行，含 28 个 `useState`、8 个 `useRef`，同时管理会话目录、历史请求、上传、语音、发送重试、模型偏好、Live2D 与页面布局。`busy`、`chatInFlightRef`、控制器和请求 ID 共同表达回合状态。
- 影响：修改一种交互时必须同时理解其他异步任务的清理、会话切换和预览资源归属，容易漏掉状态组合。长度只是该职责耦合的表现。
- 建议：先提取有生命周期的 `useChatTurn`、`useConversationHistory`、`useAttachments`；再拆形象控制和设置展示。用明确的回合状态驱动界面，而不是继续增加布尔值。保留已有语音 hook，不一次重写整个页面。
- 验收：原有九组浏览器回归继续通过；新增 hook 能独立验证成功、取消、提交中、网络状态未知和卸载；页面只组合行为与展示。

## M06 · 应用工厂没有形成隔离装配边界

- 位置：[工厂](../../app/factory.py#L10)、[模块级装配](../../main.py#L43)、[配置与基础设施全局对象](../../infrastructure/container.py#L16)、[全局服务实例](../../modules/chat_api/service.py#L167)。
- 现状：`create_app()` 导入并返回 `main.app`；`main` 导入阶段创建服务、装配注册表并注册路由。数据库、模型、情绪对象和注册表又各自使用模块全局状态。
- 影响：测试和运行环境无法自然创建两个相互隔离的应用；换临时数据库需在多个模块 patch 获取函数，失败容易受导入次序影响。
- 验证：没有进入 lifespan 的情况下，两次 `create_app()` 返回同一个对象。现有测试也需要同时 patch `get_db_path`、`get_chat_history`、记忆客户端与图执行函数。
- 建议：让工厂接受设置和少量依赖，创建新的 FastAPI 实例；路由通过应用依赖获取服务，生命周期显式管理主动循环。先注入回合服务/存储/记忆，不增加通用依赖注入框架。
- 验收：同一进程创建两个 app 使用不同临时数据库且不串状态；导入模块不启动服务或依赖真实配置；关键装配失败可被测试观察。

## M07 · 转发和错误契约缺少统一实现

- 位置：[历史代理](../../frontend/app/api/chat/history/route.ts#L7)、[在场代理](../../frontend/app/api/presence/route.ts)、[rewrite](../../frontend/next.config.ts#L6)、[错误读取](../../frontend/src/matrix/client.ts#L16)、[聊天请求](../../frontend/src/matrix/client.ts#L135)。
- 现状：部分接口由 rewrite 转发，部分 Route Handler 重复实现 fetch/超时/错误转发；历史代理忽略客户端 `limit`，写死 50，后端失败统一转成 500；其他代理又保留状态码。客户端已有 `readApiError`，但聊天和历史错误仍直接显示原始响应文本。
- 影响：定位错误要跨多层判断状态被谁改写；新增同类接口容易带入不同超时、参数和错误格式。
- 建议：保留一套薄的服务端转发工具和浏览器 JSON 请求工具；统一参数、取消信号和错误格式，保留必要的状态码。业务错误用稳定代码表达，中文提示由界面映射。
- 验收：`limit` 透传；后端 400/409/422/503 与网络失败可区分；前端提示不出现原始 JSON 包装；测试直接覆盖代理层，不能只 mock 浏览器最终地址。

## M08 · 配置读取时机和解析语义分散

- 位置：[模型与数据库配置](../../infrastructure/container.py#L16)、[主动消息配置](../../agents/proactive.py#L40)、[情绪阈值](../../state/mood_engine.py#L61)、[出图参数](../../modules/image_gen/workflow.py)。
- 现状：有些值在导入时固化，有些每次调用读取；布尔解析和数字错误处理不一致；模型、记忆、情绪与启动器分别决定部分默认值。
- 影响：测试通过环境变量覆盖设置时容易因导入次序得到旧值；配置错误可能在导入期或第一次使用时才暴露，定位方式不统一。
- 建议：建立一个范围明确的设置对象，启动时解析、校验并传入服务；按模块分组但保留现有环境变量兼容。明确哪些设置需重启，不做隐式热加载。
- 验收：布尔和数值边界、缺失项、旧别名和两套测试配置均可独立验证；错误能指出具体变量，不能输出密钥。

## M09 · 历史接口语义与适配层的用途需收敛

- 位置：[请求字段说明](../../main.py#L315)、[协议层](../../app/matrix/ports.py#L68)、[注册表](../../app/registry.py#L50)。
- 现状：当前只运行 Bina，但 OpenAPI 描述仍宣称内阁路由、开发流水线和“11 人 + Jean”；`ChatRequest` 与 `TurnRequest` 重复维护相近字段。注册表装配多个端口，当前 HTTP 聊天主路径却直接调用全局 `turn_service`，实际运行读取注册表的主要是人物目录。
- 影响：维护者和调用者难以分辨哪些字段有效、哪些是兼容承诺，误把历史抽象当作当前扩展点。
- 建议：明确兼容层边界，修正描述并集中映射；核对适配层真实调用方后再决定保留或简化，不能仅凭名称批量删除。保留 Bina 和现有兼容接口，不恢复多人物运行。
- 验收：OpenAPI、参考文档与实际行为一致；字段变更有兼容测试；运行路径和可用扩展点能由少量入口解释。

## M10 · 检查门禁和测试隔离仍依赖人工

- 位置：[依赖清单](../../requirements.txt)、[质量回归 fixture](../../test_suite/test_quality_regressions.py#L30)、[浏览器回归脚本](../../scripts/check_frontend_interactions.py)。
- 现状：前端已有 ESLint/TypeScript；仓库尚无统一 Python formatter、lint/type 配置和 CI workflow。部分测试依赖大量全局 patch，使用 `patch.stopall()`；浏览器多场景顺序执行且共享页面，前面失败会阻断后续检查。Linux 启动器测试不覆盖 Windows 入口。
- 影响：代码风格、类型与跨入口行为容易在人工检查遗漏时分叉，测试也更难定位失败属于哪一个状态组合。
- 建议：先将现有可复现命令接入 CI；渐进给改动模块配置 Python lint/type 检查；fixture 各自清理自身 patch，将浏览器场景拆成可单独运行的用例。保留已有回归，不以覆盖率数字替代行为验收。
- 验收：干净环境有一组统一检查命令；单个用例可重复独立运行；并发与平台边界分别可定位；格式化范围不扩展到无关文件。

## 建议实施批次

1. **行为边界**：M01–M03，先补失败用例，再统一入口，保留已有回合提交语义。
2. **数据与界面职责**：M04–M05，明确持久化契约后拆前端生命周期，不改变外部接口行为。
3. **装配与维护工具**：M06–M10，逐步注入依赖、统一配置和传输，收敛兼容描述并建立检查门禁。

## 本轮验证范围

- 当前完整 Python 单测 45 项通过；这说明已有用例覆盖的行为成立，不代表上述维护风险已解决。
- 完成四项独立定向实验：应用工厂身份、主动消息绕过锁、请求表加列、数据库占用时取消阻塞；另以模拟命令核对 Windows 按端口终止路径。
- 所有存储实验使用临时数据库；模型和 Windows 终止命令使用模拟对象；现有启动器回归只终止其自行创建的临时测试进程。未启动聊天服务、调用外部模型、读取真实聊天内容或执行 Windows/WSL 终止命令。
- 本轮没有修改应用实现，没有重复执行前端构建或浏览器回归；M05、M07 的结论属于静态检查，M01 的真实 Windows 行为仍需相应环境验证。
- 源码位置以检查时工作区为准，行号可能随后续修改变化。
